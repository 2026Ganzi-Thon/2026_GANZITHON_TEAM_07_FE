# 말랑이 체험 조사와 구현 계획

확인일: 2026-11-14. 사용자 요청에 따라 참고 사이트를 관찰하고 공식 기술 문서·자산 원본 페이지를 확인했다. 외부 사이트 코드·모델·음원을 복사하지 않았다. 아래의 구현 선택은 팀의 최종 캐릭터 디자인 확정과 구분한다.

## 판단

현재 모바일 웹에는 **Canvas 2D로 형태와 명암을 함께 그리는 2.5D 방식**을 먼저 적용한다. 정면에서 누르고 늘리는 체험을 빠르게 제공하면서, 누른 위치에 반응하는 변형·세 종류의 차이·소리를 검증할 수 있다. 이미지를 통째로 확대·축소하는 기존 CSS 방식의 한계를 보완한다.

실제 3D를 영구 제외한 결정은 아니다. 옆면과 뒷면을 돌려 보거나 빛에 따라 재질이 달라지는 것이 체험의 핵심이 되면, 같은 입력·인벤토리 구조에 별도 3D 렌더러를 연결한다. 모델 파일을 구하는 것만으로 부드러운 물성이 구현되지는 않는다.

## 참고 사이트에서 확인한 점

[왁뿌볼](https://www.wakbbuball.com/)에서 슬랑이의 푸딩, 스퀴시의 팥빵 등 선택 화면과 드래그 반응을 직접 확인했다. 여러 형태 선택, 재시작, 소리, 크기 설정이 있으며 조작 대상이 화면 중심을 차지한다. DOM에 포함된 스크립트에서 `WebGLRenderer`, `BufferGeometry`, `Raycaster`, `AudioContext` 식별자를 확인했다. Three.js 계열의 기하·레이캐스팅·Web Audio 구성을 사용한다는 추론은 가능하지만, 전체 소스 구조·라이브러리 버전·모델 제작 과정까지 확인한 것은 아니다. 특정 로더 식별자가 없다는 이유로 외부 모델을 전혀 쓰지 않는다고 단정하지 않는다.

우리 서비스에서 가져올 원칙은 세 가지다.

- 손을 댄 위치와 변형·파괴 위치가 연결되어야 한다.
- 종류를 바꾸면 색만 바뀌는 것이 아니라 늘어남, 되돌아옴, 껍질 반응도 달라야 한다.
- 리셋과 소리는 쉽게 찾되 대화 진입·보관함을 가리는 기능을 계속 늘리지 않는다.

랭킹·운세·수집 등 참고 사이트의 부가 기능은 현재 PRD에 추가하지 않았다. 더 나은 체험인지 판단하려면 실제 사용자가 조작하고 종류 차이를 알아보는지 확인해야 한다. 시각 효과가 많다는 것만으로 우수하다고 판단하지 않는다.

## 표현 방식 비교

| 방식 | 장점 | 한계 | 이번 판단 |
|---|---|---|---|
| CSS 그림 전체 변환 | 가볍고 첫 시안이 빠름 | 누른 곳만 찌그러지지 않음. 껍질 파괴를 세밀하게 표현하기 어려움 | 오류 시 기본 캐릭터 표시용으로 유지 |
| 변형 가능한 윤곽 + Canvas 명암 | 위치별 눌림·늘리기, 직접 만든 여러 형태, 작은 의존성 | 실제 깊이·뒷면·광학적 투명도 없음 | 현재 구현 |
| 생성/구매 이미지에 변형 효과 | 완성된 이미지의 분위기를 빠르게 적용 | 그림에 그려진 빛·얼굴까지 같이 늘어나며 임의 회전 불가 | 참고 시안·썸네일에 적합 |
| Three.js/R3F의 변형 메시 | 진짜 공간·회전·광원, 쉐이더·모프 타깃 사용 가능 | 메시 밀도·법선·변형·기기 성능을 별도 관리 | 후속 비교 후보 |
| 완전한 유체/소프트바디 시뮬레이션 | 복잡한 물성 가능 | 모바일 안정성·연산·튜닝 범위 큼 | 이번 필수 체험의 선행 조건으로 삼지 않음 |

## 이번에 넣은 형태와 조작

| 종류 | 형태 3개 | 조작 구현 | 기획 근거·임시값 |
|---|---|---|---|
| 슬랑이 | 물방울·푸딩·구름 | 접촉 위치 음영/국소 윤곽 변형, 길게 누르기·반복 누르기 깊이 증가, 큰 드래그 변형 | PRD 6.1. 입력 종료 3초 후 5초 복원 |
| 스퀴시 | 모찌·식빵·별 | 슬랑이보다 작은 늘어남, 압축·복원 | PRD 6.1. 입력 종료 3초 후 3초 복원 |
| 왁뿌볼 | 진주·하트·조약돌 | 가까운 껍질 영역부터 파괴, 짧게 떨어지는 조각, 전체 파괴 후 내부 스퀴시 조작 | 반복 접촉 파괴 요구. 12영역/회당 2영역/6회는 구현용 값 |

형태는 프로젝트에서 수학적 윤곽과 Canvas 그리기로 작성했다. 외부 캐릭터 모델을 가져오지 않았다. 아홉 가지는 새 백엔드 종류가 아니라 기존 세 종류 안의 표현 선택이다. D34에 따라 세 종류를 모두 처음부터 제공한다. 추천은 안내로만 유지한다. 선택 모양·음량은 현재 브라우저 실행 중 메모리에만 유지하며 계정 저장 API를 임의로 만들지 않는다.

윤곽점 48개에 손가락 거리 가중치를 적용하고, 스프링·감쇠로 목표 모양을 따라간다. 껍질은 독립적으로 만든 보로노이 다각형으로 나눴다. 이는 유체나 실제 재료의 물리 정확도를 보증하는 시뮬레이터가 아니다. 복원 시간과 파괴 횟수는 실사용 후 조정 가능하도록 코드에서 분리했다.

## 모바일 구현 근거

- 포인터 하나가 조작을 소유한다. 영역 밖으로 움직여도 캡처로 추적하고, 취소·창 초점 이탈·탭 숨김에서 해제한다. 터치와 마우스를 별도 제스처 시스템으로 중복 구현하지 않는다. [MDN Pointer Events](https://developer.mozilla.org/en-US/docs/Web/API/Pointer_events)
- Canvas의 물리 픽셀 비율은 최대 2로 제한한다. 화면이 작아도 DPR을 그대로 따라가면 픽셀 비용이 커지므로 실기기에서 선명도와 연산량을 함께 조정한다. [Canvas 최적화](https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API/Tutorial/Optimizing_canvas), [Three.js 해상도 설명](https://threejs.org/manual/pages/responsive.html)
- 변형 계산과 그리기는 `requestAnimationFrame` 안에서 진행한다. 정지 상태는 루프를 멈추고 복원 시작 시간에 다시 깨운다. 숨긴 탭에서는 중단한다. 포인터 입력에는 React 상태가 일부 쓰이지만 매 프레임 React로 윤곽 전체를 갱신하지 않는다. 3D 전환 시에도 고빈도 업데이트를 React 상태로 전달하지 않는 원칙을 유지한다. [R3F 성능 지침](https://r3f.docs.pmnd.rs/advanced/pitfalls)
- 줄인 모션 설정에서는 긴 복원/낙하 연출을 줄이고 손을 떼면 즉시 원래 모양으로 돌아온다. 소리는 별도 선택이며 진동 기능을 자동 추가하지 않는다.

현재 자동 검사는 데스크톱에서 실행한 모바일 Chromium/WebKit이다. 실제 중저가 Android의 발열·배터리·지속 FPS나 iPhone 오디오 출력 성능을 측정했다고 표현하지 않는다.

## 소리 선택과 출처

종류별 샘플 3개, 총 9개를 약 300KB의 mono 32kHz PCM WAV로 준비했다. OGG 원본을 앱에 그대로 넣는 대신 브라우저 공통 디코딩을 검사할 수 있는 WAV로 변환했다. 원본 파일 해시·구간·결과 피크/RMS는 `public/assets/audio/manifest.json`에 기록했다.

| 체험 | 원본 | 사용 방식과 한계 |
|---|---|---|
| 슬랑이 | rubberduck의 [40 CC0 water splash/slime SFX](https://opengameart.org/content/40-cc0-water-splash-slime-sfx) | `slime_01/05/09`. 제작자가 일부를 실제 슬라임으로 녹음했다고 설명한다. 선택한 각 파일이 전부 실제 녹음이라는 단정은 하지 않음 |
| 스퀴시 | Joseph SARDIN의 [Sponge and foam](https://bigsoundbank.com/sponge-and-foam-s0778.html) | 손으로 거품 있는 스펀지를 짜는 녹음에서 서로 다른 0.7초 구간. 건조한 빵/폼 자체의 소리와는 다름 |
| 왁뿌볼 | rubberduck의 [75 CC0 breaking/falling/hit SFX](https://opengameart.org/content/75-cc0-breaking-falling-hit-sfx) | 나무 파손 3개를 짧게 가공. 실제 왁스 파열 녹음은 아님 |

모두 원본 페이지의 CC0 표시를 확인했다. 라이브러리나 검색 결과 전체가 같은 라이선스라고 가정하지 않는다. Freesound는 파일마다 조건이 다르므로 로그인이나 추가 권리 확인이 필요한 후보를 이번 번들에 넣지 않았다. [Freesound FAQ](https://freesound.org/help/faq/)

사용자가 소리를 켜기 전에는 AudioContext 생성·음원 요청·자동 재생을 하지 않는다. 짧은 버퍼를 준비하고, 3개 변형을 순환하며 재생 속도를 소폭 바꾼다. 연속 드래그는 발음 간격을 제한하고 활성 음성 4개를 넘으면 가장 오래된 음성을 25ms 안에 페이드아웃한다. 음량 0·음소거·체험 종료·탭 숨김은 재생을 멈춘다. 다운로드 실패 때는 짧은 합성 효과로 대체하고 설정에 상태를 표시한다. [Web Audio 권장 사항](https://developer.mozilla.org/en-US/docs/Web/API/Web_Audio_API/Best_practices)

클리핑 방지·채널·길이·브라우저 디코딩은 검사하지만, 실제 스피커/이어폰 청취 품질은 별도 확인해야 한다. 기본 음량 35%와 음소거 시작은 이번 구현 선택이며 팀 최종 사운드 가이드로 확정하지 않는다.

## 실제 3D로 갈 경우의 작업 순서

1. **대표 형태 하나로 비교한다.** 물방울이나 둥근 모찌를 직접 모델링해 현재 Canvas 버전과 같은 제스처로 평가한다. 아홉 모델부터 구매하지 않는다.
2. **변형 가능한 토폴로지를 만든다.** 표면에 고르게 분포한 꼭짓점, 단순 재질, 몸/껍질 분리 구조가 필요하다. 삼각형 수가 많거나 복잡한 장식이 있다는 이유만으로 좋은 변형 모델이 되지 않는다. [Three.js 사용자 정의 기하](https://threejs.org/manual/pages/custom-buffergeometry.html)
3. **고정 변형과 임의 접촉을 구분한다.** Blender shape key는 눌림/늘림의 고정 형태를 만들고 glTF morph target으로 전달할 수 있다. 손가락이 닿는 임의 위치는 레이캐스팅 뒤 꼭짓점 또는 셰이더 변형을 추가해야 한다. [Blender glTF 내보내기](https://docs.blender.org/manual/en/5.2/addons/scene_gltf2.html)
4. **재질을 절제한다.** 투명·굴절·물리 재질은 비용이 더 크다. 기본 조명과 단순 재질부터 시작하고 실제 기기 측정 후 고급 효과를 추가한다. [MeshPhysicalMaterial](https://threejs.org/docs/pages/MeshPhysicalMaterial.html)
5. **자산은 권리와 적합성을 함께 본다.** 직접 제작이 우선 후보다. 외부 후보는 배포·수정·재배포 조건, 폴리곤 수, 텍스처 용량, 메시 구조를 확인한다. Kenney와 Poly Haven은 CC0 자료 후보지만 특정 말랑이 모델이 준비되어 있다는 뜻은 아니다. [Kenney](https://kenney.nl/support), [Poly Haven 라이선스](https://polyhaven.com/license)

## 다음 검수와 판단 기준

- 같은 제스처에서 세 재료의 차이가 눈에 보이는가.
- 손 위치와 눌림/껍질 파괴가 맞는가. 빠르게 연속 조작해도 좌표가 튀거나 소리가 쌓이지 않는가.
- 리셋·모양 변경·메인 복귀·상담 진입 후 눌림/오디오가 남지 않는가.
- 360/390/430px, 가로 화면, 키보드·줄인 모션에서도 조작과 모달이 접근 가능한가.
- 실제 휴대폰에서 첫 오디오 활성화, 무음 상태, 앱 전환 복귀, 2분 연속 조작을 확인한다.
- 팀의 정식 캐릭터 자산과 비교한 뒤 Canvas 유지/3D 전환을 정한다. 최종 인증·AI·기록 연동을 미루면서 후순위 효과를 늘리지 않는다.

실행한 자동 검사와 실패 수정 내역은 [QA 검증 기록](qa.md), 기능별 실제/임시/미연동 상태는 [필수 기능 현황](requirements-status.md)에 기록한다.

## 이번 검수 결과

단위 53개, 기존/신규 브라우저 고유 108개 시나리오 범위를 확인했다. 발견한 메인 초점 복귀 시 10px 이동을 수정했고, 같은 위치·같은 조작 요소를 유지하는지 두 브라우저에서 재검증했다. 9개 형태·국소 그림 변화·복원 종료·껍질과 내부 조작을 검사했다. 실행별 실패와 수정은 일지에 보존했다.

음원 9개는 Chromium에서 디코딩·신호 범위·음량/음소거·다운로드 실패 대체·재활성화 회복을 확인했다. PCM 원본의 피크와 브라우저 재표본화 후 피크를 동일 수치로 취급하지 않으며 디코딩 후 full-scale 미만을 검사했다. 이 PC의 Playwright WebKit 빌드는 Web Audio API를 제공하지 않으므로 미지원 UI·조작 지속만 확인했다. 이를 iPhone Safari 소리 검수로 대체할 수 없다.
